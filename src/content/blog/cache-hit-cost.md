很多人第一次看到 cacheRead 价格只有 input 的十分之一时，会以为这是运营手段。其实它反映的是真实的工程现实：服务端对命中缓存的请求，几乎不需要重新跑前向计算。

对于聊天、Agent、工具调用这类"多轮 + 长上下文"的工作负载，每一轮新请求里都有大量重复内容——系统提示没变，历史对话没变，只有新增的那一小段是真正的新输入。这意味着你的实际账单大头，往往不是"新 input"，而是"命中缓存的重复 input"。

我们默认用 90/9/1 的混合比例（90% 缓存读取、9% input、1% output）来估算订阅池的配额，因为这是长会话类负载的典型画像。如果你跑的是批量离线推理、很少复用上下文，那你的真实结构会向 input 倾斜，90/9/1 的结论就不适用了——这时缓存读取几乎帮不上忙，纯 input 单价反而更接近真相。这也是为什么我们在每个订阅商详情页同时展示 quota90 与 quota95 两档：缓存策略激进与否，配额数字差别巨大。

另一个容易被忽略的是缓存**写入**。有些服务商对第一次写入缓存的内容单独收费，有些则把写入成本揉进读取价里（也就是 cacheWrite 记 null，不单列）。如果只比较 cacheRead 而忽略 cacheWrite，你会误以为"缓存免费"的那家更便宜——实际上它可能把写入费摊进了更高的读取单价里。

所以正确的记账方式是：先把你的调用日志按命中/未命中拆开，测出真实的缓存命中率；再确认目标服务商是否单列 cacheWrite；最后用你自己的混合比例去套加权成本。**别人的 90% 命中率不等于你的 90%**——除非你的 prompt 是模板化的、历史是复用的，否则别默认自己享受了缓存红利。
